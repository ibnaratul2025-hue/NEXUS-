# Digital World Model & Universal Action Fabric

This document provides a deep technical explanation of the **NEXUS Digital World Model** and **Universal Action Fabric**, introduced in Phase 7.

---

## 1. Digital World Model Engine (`WorldModelEngine`)

The Digital World Model transforms NEXUS from a conversational prompt processor into an environment-aware operating intelligence.

### 1.1 Ontological Entity Domains
The World Model maintains live structured representations across 15 discrete domains:

1. `USER`: Identity, preferences, trust parameters, active focus.
2. `DEVICE`: Hardware status, battery level, thermals, storage, network connectivity.
3. `APP`: Installed applications, package names, declared capabilities, export activities.
4. `FILE`: Sandboxed files, documents, configuration state.
5. `PROJECT`: Long-running user undertakings linking multiple files, tasks, and goals.
6. `TASK`: Granular sub-units of work awaiting execution or validation.
7. `DOCUMENT`: Structured knowledge items, manuals, and persisted references.
8. `SKILL`: Synthesized or built-in procedural automations.
9. `MISSION`: Multi-step autonomous goals running in the background.
10. `PERMISSION`: Android OS runtime permissions and grant statuses.
11. `NOTIFICATION`: Incoming device alerts classified by priority and actionability.
12. `SETTING`: Toggles, volume levels, display mode, attention state.
13. `CONNECTED_DEVICE`: Local peripherals (watches, tablets, desktop mesh nodes).
14. `AVAILABLE_SERVICE`: Local background services or system daemons.
15. `CURRENT_CONTEXT`: Ephemeral runtime state (foreground app, time of day).

### 1.2 Bidirectional Semantic Relations
Entities are linked into a queryable semantic graph through typed edges:
- `USES`: e.g. `(User) -USES-> (YouTube App)`
- `OWNS`: e.g. `(User) -OWNS-> (Research Project)`
- `DEPENDS_ON`: e.g. `(Skill) -DEPENDS_ON-> (File Sandbox)`
- `RUNNING`: e.g. `(Device) -RUNNING-> (Mission #104)`
- `AVAILABLE`: e.g. `(Device) -AVAILABLE-> (Camera Provider)`
- `REQUIRES`: e.g. `(Action) -REQUIRES-> (READ_CONTACTS Permission)`
- `CREATED_BY`: e.g. `(Skill) -CREATED_BY-> (NEXUS Learning Engine)`
- `RELATED_TO`: e.g. `(Note.txt) -RELATED_TO-> (Research Project)`
- `BLOCKED_BY`: e.g. `(Mission) -BLOCKED_BY-> (Pending User Confirmation)`
- `CAN_EXECUTE`: e.g. `(Device) -CAN_EXECUTE-> (System Action Fabric)`

### 1.3 The Epistemic Invariant
To prevent hallucination from contaminating the knowledge graph, NEXUS strictly enforces four epistemic categories:

```kotlin
enum class EpistemicStatus {
    FACT,        // Direct ground truth verified via Android OS APIs (Confidence = 1.0)
    OBSERVATION, // Transient sensory input directly witnessed (Confidence = 1.0)
    PREDICTION,  // Projected state generated by model reasoning (Confidence <= 0.95)
    ASSUMPTION   // Unverified working heuristic; must be flagged (Confidence <= 0.75)
}
```

- **Invariant Rule**: A `PREDICTION` or `ASSUMPTION` can **never** be promoted to a `FACT` until an actual `ToolReceipt` or system API confirms the state transition in the real world.

## 2. Universal Action Fabric (`ActionFabric`)

The Action Fabric is the universal execution bridge between intent and real-world system mutation.

### 2.1 Action Definition Schema
```kotlin
data class UniversalAction(
    val capability: String,
    val target: String,
    val parameters: Map<String, Any?> = emptyMap(),
    val requiredPermissions: List<String> = emptyList(),
    val risk: RiskLevel = RiskLevel.LOW,
    val description: String = "",
    val verificationRule: String? = null,
    val rollbackAction: (suspend (ActionContext) -> Boolean)? = null,
    val execute: suspend (ActionContext) -> ActionExecutionResult
)
```

### 2.2 Built-in Public Actions
- `open_app`: Dispatches explicit launch intent via `PackageManager`.
- `open_url`: Opens valid web URLs in default browser.
- `read_file` / `create_file` / `move_file`: Manages sandboxed files with verification and undo.
- `launch_intent`: Sends structured Android intents (view, send, dial).
- `change_setting`: Adjusts permitted system toggles (e.g. night mode, attention mode).
- `send_share_intent`: Dispatches data to other applications via Android share sheets.
- `create_reminder`: Adds local notification reminders.
- `run_skill`: Invokes a verified synthesized skill.
- `start_mission`: Spawns an autonomous background goal in `MissionEngine`.

### 2.3 Universal Undo & Reversibility
Any action that mutates state provides a `rollbackAction` lambda. When executed, an `ActionHistoryEntity` is recorded in the Room database. If a mission fails or the user requests an undo, `UniversalUndoManager` executes the inverse operation atomically.

## 3. Capability Negotiator & 6-Stage Gating

Before any action is invoked, the `CapabilityNegotiator` runs a deterministic 6-stage validation:

```
[Intent Proposed]
       │
       ▼
 1. Can I do this? ─────────────► (Capability exists in ontology?)
       │ Yes
       ▼
 2. Is capability available? ───► (Tool / Adapter registered in ActionFabric?)
       │ Yes
       ▼
 3. Is permission granted? ─────► (Android runtime permission check)
       │ Yes
       ▼
 4. Is target available? ───────► (Package installed / file exists / hardware ready?)
       │ Yes
       ▼
 5. Is action safe? ────────────► (PolicyEngine check: Low / Medium / High / Critical)
       │ Pass / Confirmed
       ▼
 6. Can result be verified? ────► (Verification rule present?)
       │ Yes
       ▼
 [EXECUTE & CAPTURE RECEIPT]
```

### Non-Hallucination Guarantees
If any stage fails, the negotiator returns `NegotiationResult.Limitation`, citing:
- Exact technical reason for failure.
- Prerequisites required to unlock the capability.
- Suggested alternatives without fabricating APIs.

## 4. Sandboxed App Adapter SDK

Developers can extend NEXUS with community adapters without granting arbitrary code execution:

```kotlin
interface AppAdapter {
    val appId: String
    val appName: String
    val version: String
    val capabilities: List<String>
    val requiredPermissions: List<String>
    val actions: List<AdapterActionDefinition>
    suspend fun execute(context: Context, actionName: String, parameters: Map<String, Any>): ActionExecutionResult
}
```

- **User Approval Requirement**: Third-party adapters are registered in an unapproved state by default. The user must explicitly approve the adapter in the **Decision Center** before actions can execute.
- **Privilege Isolation**: Adapters run strictly within the app's sandboxed security boundaries and cannot access private Android OS APIs.

## 5. Accessibility Controller & Hardware Emergency Stop

### 5.1 Semantic UI Traversal
The `AccessibilityController` navigates the Android view hierarchy using semantic selectors:
- `resourceId`: Android view resource identifier (e.g. `com.example.app:id/submit_button`).
- `text`: Visible button or label text.
- `contentDescription`: Accessibility content description.
- `className`: Android widget class (e.g. `android.widget.Button`).

### 5.2 Hardware Emergency Stop
A global atomic kill switch is integrated into the accessibility pipeline:
- If `isEmergencyStopped == true`, all ongoing accessibility operations abort immediately.
- Users can trigger Emergency Stop from the notification tray, the floating JARVIS HUD, or the Decision Center.

## 6. Deterministic Workflow Compiler (`WorkflowCompiler`)

Natural language automations (e.g. *"Whenever I start studying, silence notifications and open my notes"*) are compiled into 5-stage deterministic automata:

1. **TRIGGER**: Voice keyword, time schedule, battery state, or app launch.
2. **CONDITIONS**: Device state requirements (e.g. Wi-Fi connected, battery > 20%).
3. **ACTIONS**: Ordered list of verified `ActionFabric` steps.
4. **VERIFICATION**: Post-execution assertions confirming successful state change.
5. **FAILURE HANDLING**: Rollback actions or fallback notifications.

Compiled workflows require user confirmation before being armed in the local database.
